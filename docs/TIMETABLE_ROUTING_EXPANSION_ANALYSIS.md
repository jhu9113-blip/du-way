# 시간표 기반 실제 길안내 확장 분석

> 작성 기준: 2026-08-12  
> 기준 문서: `docs/PRD.md`, `docs/DEVELOPMENT_PLAN.md`  
> 기준 코드: Next.js 16.3.0 App Router, React 19, TypeScript 5.7

## 1. 문서 목적

현재 DU WAY 프로토타입을 다음 제품 흐름으로 확장할 수 있는지 분석하고, 필요한 화면·데이터·경로 계산 구조와 구현 순서를 정리한다.

1. 사용자가 에브리타임처럼 본인의 시간표를 직접 입력한다.
2. 각 수업을 캠퍼스 건물 및 강의실과 연결한다.
3. 현재 시각을 기준으로 직전 수업과 다음 수업을 자동으로 찾는다.
4. 직전 수업 건물에서 다음 수업 건물까지 빠른 경로 또는 무장애 경로를 안내한다.
5. 수업 사이 이동 가능 여부와 권장 출발 시각을 보여준다.

이 문서는 구현 계획 수립 전의 구조 분석 문서이며, 현재 코드를 변경한 결과를 의미하지 않는다.

## 2. 결론

현재 코드베이스를 바탕으로 구현 가능하다. 시간표 카드, 건물 ID 연결, 이동 조건 설정, 경로 결과 UI, SVG 지도 등 재사용 가능한 기반이 이미 존재한다.

다만 현재 경로는 `성산홀 → 경상대학` 한 구간의 고정 결과이므로 시간표 편집 UI만 추가해서는 실제 기능이 완성되지 않는다. 다음 세 영역을 함께 전환해야 한다.

- 사용자별 시간표 입력·수정·삭제와 영속화
- 시간표를 기반으로 직전·다음 수업과 출발·목적지를 계산하는 로직
- 임의의 건물 조합에 대해 경로를 찾을 수 있는 캠퍼스 경로 데이터와 탐색 엔진

초기 MVP는 주요 건물 쌍의 사전 계산 경로를 조회하는 방식으로 시작할 수 있다. 실제 노드·간선 데이터가 확보되면 Dijkstra 또는 A* 기반 동적 계산으로 전환하는 것이 현실적이다.

## 3. 현재 PRD 범위와 구현 상태

현재 PRD는 외부 연동이 없는 발표용 프런트엔드 프로토타입을 정의한다.

### 현재 제공 기능

- 이동 수단과 경로 선호 조건 온보딩
- 고정된 다음 수업과 권장 출발 시각을 표시하는 홈
- 월요일 수업 2개를 보여주는 읽기 전용 시간표
- 빠른 경로와 무장애 경로 비교
- 외부 지도 SDK가 없는 자체 SVG 지도
- GPS 실패 및 경로 없음 시연
- 관리자용 건물·시설·경로·데모 데이터 편집 화면
- React Context와 `useReducer` 기반 브라우저 메모리 상태

### 현재 제외된 기능

- 회원가입, 사용자 로그인 및 사용자 식별
- 데이터베이스와 서버 API
- 사용자별 시간표 영속화
- 시간표 추가·수정·삭제
- 실제 현재 시각 및 GPS 기반 출발지 결정
- 임의 건물 사이의 경로 계산
- 설정에 따른 경로 재계산
- 실제 캠퍼스 전체 건물·보행로·접근성 실측 데이터

### 현재 데이터 규모

- 건물 4개: 경상대학, 성산홀, 정보통신대학, 중앙도서관
- 시설 6개: 엘리베이터 2, 경사로 2, 계단 1, 급경사 1
- 수업 2개: 월요일 성산홀 수업과 경상대학 수업
- 경로 2개: 같은 건물 쌍에 대한 빠른 경로와 무장애 경로

## 4. 현재 코드 구조 분석

### 사용자 상태

`lib/store.tsx`는 다음 데이터를 브라우저 메모리에 관리한다.

```ts
type AppState = {
  onboarded: boolean
  settings: Settings
  courses: Course[]
  demoNow: string
  demoGpsFailed: boolean
  demoNoRoute: boolean
}
```

수업 추가·삭제 reducer 액션은 존재하지만 사용자 화면에서 호출하지 않으며, 새로고침하면 모든 값이 초기화된다.

### 관리자·데모 상태

`lib/editable-demo-store.tsx`는 건물, 시설, 고정 경로, 수업과 발표용 다음 수업 정보를 별도로 관리한다. 사용자 페이지 일부도 이 Store의 데이터를 사용하므로 사용자 상태와 관리자 데모 상태가 중복되어 있다.

운영 구조로 전환할 때는 다음처럼 역할을 분리해야 한다.

- 서버 데이터: 사용자, 시간표, 건물, 시설, 경로 그래프
- 사용자 세션 상태: 로그인 사용자, 현재 선택 요일, 현재 위치, 임시 입력값
- 화면 상태: 모달, 탭, 로딩, 오류
- 시연 상태: 운영 코드에서 분리하거나 개발 환경 전용으로 제한

### 시간표 화면

`app/timetable/page.tsx`는 모든 수업 중 월요일(`day === 1`)만 필터링해 카드 목록으로 표시한다. 다음 수업 여부는 수업 ID나 현재 시각이 아니라 고정된 데모 수업명과 비교한다.

현재 화면 하단에도 시간표 편집이 시연 범위에 포함되지 않는다고 명시되어 있다.

### 경로 화면

`app/route/page.tsx`는 사용자가 선택한 수업이 아니라 고정된 데모 출발지와 목적지를 사용한다. `FAST`, `ACCESSIBLE` 두 경로 역시 `data/mock.ts`에 정의된 고정 결과다.

### 도메인 타입

현재 `Course`에는 수업 장소 연결에 필요한 기본 필드가 이미 있다.

```ts
type Course = {
  id: string
  name: string
  day: 1 | 2 | 3 | 4 | 5
  startTime: string
  endTime: string
  buildingId: string
  room: string
}
```

`buildingId`를 기준으로 건물을 연결하는 구조는 유지할 수 있다. 건물명을 자유 텍스트로만 저장하면 오타와 별칭 때문에 경로 계산이 불가능하므로, 검색 결과에서 등록된 건물을 선택하게 해야 한다.

## 5. 권장 메뉴와 사용자 흐름

새 하단 메뉴를 추가하기보다 기존 `시간표` 메뉴를 시간표 관리의 중심으로 확장하는 것이 적합하다. 모바일 하단 탭은 홈·시간표·길안내·설정 네 개를 유지한다.

```text
/timetable
├─ 주간 시간표
├─ 오늘의 수업 목록
├─ 수업 추가
└─ 수업 선택
   ├─ 수정
   ├─ 삭제
   └─ 길안내
```

권장 라우트는 다음과 같다.

- `/timetable`: 주간 시간표와 오늘 수업
- `/timetable/new`: 수업 등록
- `/timetable/[courseId]/edit`: 수업 수정
- `/route?courseId=<courseId>`: 선택한 수업으로 길안내

별도 페이지 방식은 현재 App Router 구조와 잘 맞고 모바일 키보드, 브라우저 뒤로 가기, 접근성 관리가 단순하다.

### 수업 입력 항목

- 수업명
- 요일
- 시작 시간
- 종료 시간
- 건물 검색 및 선택
- 강의실

### 입력 검증

- 시작 시간이 종료 시간보다 빨라야 한다.
- 동일 요일의 기존 수업과 시간이 겹치지 않아야 한다.
- 건물은 등록된 `buildingId` 중 하나여야 한다.
- 수업명, 요일, 시간, 건물, 강의실은 필수로 처리한다.
- 삭제 전 확인 절차를 제공한다.

## 6. 수업 장소와 건물 연결

건물 입력은 자유 텍스트 저장이 아니라 검색·선택 방식으로 구성한다.

1. 사용자가 `경상대`, `경상관`처럼 건물명 또는 별칭을 검색한다.
2. `Building.name`과 `Building.aliases`를 대상으로 후보를 보여준다.
3. 사용자가 하나를 선택하면 수업에 `buildingId`를 저장한다.
4. 강의실은 건물과 별도의 문자열로 저장한다.

건물 검색 결과가 없을 때 사용자가 임의 건물을 생성하게 하면 경로 노드가 없어 길안내가 불가능하다. 미등록 건물은 관리자 등록 요청 안내를 보여주는 편이 안전하다.

## 7. 직전·다음 수업 자동 계산

현재 `lib/demo.ts`의 고정 `DEMO` 값은 파생 데이터 계산으로 대체해야 한다.

```text
현재 날짜와 시각
  → 오늘 요일의 수업 조회
  → 시작 시간순 정렬
  → 아직 시작하지 않은 가장 가까운 수업 선택
  → 그 수업보다 앞선 가장 가까운 수업 탐색
  → 직전 수업 건물을 출발지로 결정
  → 다음 수업 건물을 목적지로 결정
  → 경로 시간과 설정 버퍼를 반영해 권장 출발 시각 계산
```

예시:

```text
09:00~10:20 성산홀
10:30~12:00 경상대학

쉬는 시간: 10분
경로 예상 시간: 11분
도착 여유 설정: 3분
필요 이동 시간: 14분
결과: 4분 부족 경고
```

직전 수업이 없을 때는 출발지를 별도로 결정해야 한다. 단계별 권장 방식은 다음과 같다.

1. MVP: 사용자가 현재 위치 건물을 직접 선택
2. 확장: 설정에 기본 출발지 저장
3. 운영: GPS 좌표에서 가장 가까운 경로 노드 탐색

GPS 권한 거부나 신호 실패 시에는 현재 구현의 복구 UI를 활용해 출발 건물 선택으로 전환할 수 있다.

## 8. 실제 최단 경로에 필요한 데이터 구조

현재 `RouteResult`는 계산 결과를 표시하기 위한 타입이며, 경로를 탐색할 그래프의 간선 데이터가 없다. 다음 구조가 추가로 필요하다.

```ts
type PathEdge = {
  id: string
  fromNodeId: string
  toNodeId: string
  distanceM: number
  durationSec: number
  accessible: boolean
  hasStairs: boolean
  slopeLevel: 'GENTLE' | 'NORMAL' | 'STEEP'
}
```

그래프 구성은 다음과 같다.

```text
Building
  └─ entranceNodeIds

PathNode
  ├─ 건물 출입구
  ├─ 보행로 교차점
  ├─ 경사로
  ├─ 계단
  ├─ 엘리베이터
  └─ 일반 경유점

PathEdge
  ├─ 연결 노드
  ├─ 거리와 예상 시간
  ├─ 계단 여부
  ├─ 경사 수준
  └─ 접근 가능 여부
```

### 경로 계산 정책

- 빠른 경로: 거리 또는 예상 시간을 비용으로 사용하는 Dijkstra/A*
- 계단 회피: 계단 간선을 제외하거나 통행 불가로 처리
- 무장애 경로: `accessible === false`인 간선을 제외
- 엘리베이터 우선: 엘리베이터 연결 간선의 상대 비용 감소
- 완만한 경사 우선: 급경사 간선의 비용 증가 또는 제외
- 최단 거리 우선: 시간보다 거리 가중치를 높임

현재 `Settings`의 다음 필드는 이 비용 정책에 그대로 활용할 수 있다.

- `avoidStairs`
- `preferElevator`
- `preferGentleSlope`
- `minimizeDistance`
- `bufferMinutes`

## 9. 권장 데이터 흐름

```text
사용자 시간표 입력
    ↓
수업과 buildingId 저장
    ↓
현재 시각 기준 직전·다음 수업 계산
    ↓
출발 건물과 목적지 건물 결정
    ↓
양쪽 건물의 출입구 노드 조회
    ↓
사용자 이동 설정을 반영한 경로 탐색
    ↓
RouteResult 생성
    ↓
홈·시간표·길안내·지도에서 동일 결과 사용
```

홈과 시간표가 서로 다른 데모 값을 갖지 않도록 다음 수업, 권장 출발 시각, 부족 시간은 모두 동일한 계산 함수 또는 서버 서비스에서 파생해야 한다.

## 11. 데이터베이스·회원 기능 확장 시 권장 경계

회원가입과 사용자별 시간표를 도입할 경우 최소한 다음 엔터티가 필요하다.

```text
User
UserSettings ── User와 1:1
Course ───────── User와 N:1
Building
Facility
PathNode
PathEdge
```

핵심 소유권 규칙:

- 시간표와 이동 설정은 사용자 소유 데이터다.
- 건물, 시설, 노드, 간선은 모든 사용자가 공유하는 운영 데이터다.
- 사용자는 본인의 수업만 조회·수정·삭제할 수 있어야 한다.
- 관리자는 사용자 시간표가 아니라 공용 캠퍼스 데이터를 관리한다.
- 현재 하드코딩 관리자 인증은 운영 보안 수단으로 사용할 수 없다.

Neon 같은 PostgreSQL을 도입하더라도 브라우저에서 DB에 직접 연결하지 않는다. Next.js 서버 계층을 통해 인증과 소유권 검사를 거친 뒤 데이터를 읽고 써야 한다.

## 12. 단계별 구현 권장 순서

### 1단계: 시간표 편집 MVP

- 주간 시간표 UI
- 수업 추가·수정·삭제
- 건물 검색·선택
- 시간 중복 검증
- 임시 로컬 또는 서버 저장 경계 정리

### 2단계: 시간표 파생 정보

- 오늘 수업 계산
- 직전·다음 수업 자동 선택
- 수업 간 쉬는 시간 계산
- 사용자 버퍼를 반영한 권장 출발 시각과 부족 경고

### 3단계: 건물 쌍 기반 경로 MVP

- 주요 건물 쌍별 빠른·무장애 경로 저장
- 출발·목적지 건물에 맞는 경로 조회
- 경로가 없는 건물 조합의 대체 안내

### 4단계: 실제 그래프 경로 탐색

- 캠퍼스 노드·간선 스키마
- Dijkstra/A* 계산 서비스
- 이동 설정별 가중치 적용
- 경로 결과 캐시 및 검증

### 5단계: 사용자·데이터베이스 운영화

- 회원가입·로그인
- 사용자별 시간표와 설정 저장
- 서버 측 입력 검증과 소유권 검사
- 관리자 공용 데이터 영속화
- 마이그레이션, 백업, 오류 관측

### 6단계: 실제 위치 연동

- GPS 권한 요청
- 좌표를 가장 가까운 경로 노드에 연결
- 실패 시 출발 건물 직접 선택

## 13. 핵심 위험요소

| 위험 | 영향 | 대응 |
|---|---|---|
| 건물 데이터 부족 | 수업 장소를 선택할 수 없음 | 실제 수업 건물 목록과 별칭 우선 확보 |
| 경로 그래프 미실측 | 최단·무장애 안내의 신뢰성 부족 | 현장 조사와 관리자 검수 절차 도입 |
| 자유 텍스트 건물 입력 | 경로 계산 실패 | 등록 건물 검색·선택 강제 |
| 고정 데모 값 잔존 | 화면별 다음 수업 정보 불일치 | 단일 파생 계산 서비스로 통합 |
| 두 Context의 데이터 중복 | 사용자와 관리자 화면 결과 불일치 | 서버 데이터 중심으로 Store 역할 재설계 |
| 접근성 경로 가중치 오류 | 안전하지 않은 안내 가능 | 통행 불가 조건은 가중치가 아니라 간선 제외로 처리 |
| 하드코딩 관리자 계정 | 운영 보안 취약 | 실제 운영 전 서버 인증으로 교체 |

## 14. 구현 착수 전 결정 사항

다음 항목을 확정한 뒤 상세 개발 계획을 작성해야 한다.

1. 1차 범위를 시간표 편집까지만 할지, 건물 쌍 경로 조회까지 포함할지
2. 회원가입·로그인을 1차부터 포함할지
3. 첫 운영 대상 건물과 별칭 목록
4. 건물 쌍별 사전 경로와 동적 그래프 탐색 중 초기 방식
5. 직전 수업이 없을 때 출발지를 선택하는 방식
6. 학기·연도·주차 또는 반복 시간표 지원 범위
7. 관리자 공용 데이터와 사용자 개인 데이터의 저장·검수 책임
